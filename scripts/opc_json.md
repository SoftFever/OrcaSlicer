# opc_json

Decode a per-vendor `<vendor>.opc` preset cache to editable JSON, and rebuild the
cache after editing the JSON. It uses the build's own `VendorCacheFile` and
config JSON serialization, so the decoded values are exactly what the slicer
would read.

This is a CLI workaround, not an in-app Python plugin: the application exposes no
Python binding for cache I/O.

## Build

The tool is part of the `ORCA_TOOLS` dev-utils:

```bash
cmake -S . -B build -DORCA_TOOLS=ON
cmake --build build --target opc_json
```

`scripts/opc_json.sh` (and `scripts\opc_json.bat` on Windows) finds an existing
build tree, builds the target if needed, and runs it. Set `ORCA_BUILD_DIR`,
`ORCA_CONFIG`, or `ORCA_NO_BUILD=1` to override the defaults.

## Decode

```bash
./scripts/opc_json.sh decode resources/profiles/BambuLab.opc -o /tmp/BambuLab.json
```

The vendor name is taken from the input file's stem, so a file named differently
needs `--vendor <name>`. Without `-o`, the output is `<input>.json` beside the
input. The input cache is never written.

## Edit and rebuild

```bash
./scripts/opc_json.sh encode /tmp/BambuLab.json -o /tmp/BambuLab.opc
```

`encode` requires an explicit output path and refuses to write over its JSON
input. The rebuilt cache is a normal `.opc`; install it as you would the one
generated by `build_preset_cache`.

## Local install

Copy the rebuilt `<vendor>.opc` into the `resources/profiles` directory used by
the build or installed app — the same place `scripts/build_preset_cache.sh`
writes caches. Restart the app so the vendor cache is reloaded.

A cache is only served when its stamped version is at least the version of the
`<vendor>.json` sitting beside it, so lowering `vendor_version` makes the cache
stale. Keep the matching `<vendor>.json` in place unless you are deliberately
using the cache-only shipping layout; `scripts/build_preset_cache.sh` performs
that packaging step.

## JSON shape

```json
{
  "format": "orcaslicer-opc-json",
  "format_version": 1,
  "vendor_name": "BambuLab",
  "vendor_version": "02.00.00.00",
  "vendors": { "BambuLab": { "name": "...", "id": "...", "models": [ ... ] } },
  "process_entries": [
    {
      "name": "...",
      "sub_path": "...",
      "inherits": "...",
      "includes": [],
      "description": "...",
      "instantiation": "true",
      "setting_id": "...",
      "filament_id": "",
      "renamed_from": [],
      "config": { "layer_height": "0.2", "...": "..." }
    }
  ],
  "filament_entries": [],
  "machine_entries": [],
  "parse_errors": 0
}
```

`config` is a regular preset JSON object and holds only options. Entry metadata
(`inherits`, `includes`, `description`, `instantiation`, `setting_id`,
`filament_id`, `renamed_from`) sits beside it and is copied field by field.
Inheritance and includes are stored as names and are not resolved, so rebuilding
needs no profiles directory. Vendor model `technology` is `FFF`, `SLA`,
`Unknown`, or `Any`; an integer enum value is also accepted on encode.

## Build-schema dependency

Option names and types come from the build's `print_config_def`. Decoding a cache
written by a newer build drops options that build knows and this one does not —
the same lossy behavior as the slicer's own cache loader. Use the build whose
schema matches the profiles being edited, and re-decode after switching builds.
`encode` rejects unknown option names instead of letting the cache writer drop
them silently, and validates the vendor name, vendor map id, and version stamp.
